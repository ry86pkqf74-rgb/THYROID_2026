## 5. Lineage contract (object-level)

**Machine contract:** [`lineage_contract_matrix.csv`](lineage_contract_matrix.csv) + per-object SQL under [`object_level_sql/`](object_level_sql/) (generated by `run_lineage_audit.py`).

**Scope:**

- **Catalog:** `Thyroid 2026` only.
- **Schemas:** `main`, `qa`, `v2_stage`, latest release schema **`release_20260409`**.
- **Five key families tested (row-grain only):** patient (`research_id` or documented substitute), origin, time, linkage context, build/release provenance.

**Not row-grain (N/A in matrix):** aggregates (`*_summary_v`, `master_patient_rollup_verified_v1`, deduped consumption views, etc.), and control tables like `qa.release_manifest`.

**Release-critical surfaces (interpretation):**

- **`main.canonical_extracted_fact_long_v2`:** PARTIAL overall — `research_id`, `note_row_id`, `extraction_run_id` solid; **`entity_date` sparse**; **episode IDs** require join (not a schema bug per se).
- **`master_*_verified_v1` (long + lineage):** same pattern as canonical for sparse dates + linkage join (see CSV).
- **Labs (`longitudinal_lab_canonical_v1`, `thyroglobulin_lab_canonical_v1`):** **PASS** with **documented lab-grain linkage exception** (patient + temporal + wave; no `surgery_episode_id` on row).
- **`note_extraction_runs`:** **PASS (exception)** — run-grain registry, not patient-grain.
- **`main.clinical_notes_long`:** **PASS** with **documented staging/PHI exception** — workbook/excel anchors + ingest metadata; **manuscript traceability claims must not rest on raw note text in MotherDuck**.
- **FHIR resource tables:** **PARTIAL (exception)** — `patient_fhir_id` + `specimen_id` semantics per contract §Specimen + FHIR.

**Legacy `main` tables:** Many **FAIL** the strict five-key rubric; they are **out of scope** for “publication row-level traceability” unless explicitly promoted — see CSV.
